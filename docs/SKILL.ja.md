# マルチエージェント委譲の規律（空振り・無言失敗の防止）

これはリポジトリルートの [SKILL.md](../SKILL.md)（英語・正典）の日本語版です。内容が
食い違う場合は英語版を正とします。

司令塔（オーケストレーター）エージェントがサブエージェントへ作業を委譲するときに、
「空振り」（成功に見える完了通知なのに成果物ゼロ）と「無言失敗」（実行環境差で成功した
フリになる）を防ぐための規律です。

## いつ使うか

- サブエージェントに委譲したら、自分で作業せず子エージェントへ再委譲して「待ちます」と
  だけ返し、成果物ゼロで完了通知が来た。
- 完了通知の文面は成功なのに、`git status --porcelain` やファイル実在確認で変更が
  見つからない。
- 委譲プロンプトをこれから書くとき（予防として必須文言を確認する）。
- レビューで大量の指摘が出て、並列サブエージェントへ安全に展開したいとき
  （「台帳=委譲spec」の節を参照）。

## 大原則

サブエージェントの完了通知は「主張」であって「証拠」ではない。成果物を検証してから
次工程へ進み、検証してから上位へ報告する。

## ツール対応（可搬性）

この skill の原則はツール非依存です。本文中の具体名は次のように読み替えます:

- Claude Code: `Agent` ツールがサブエージェントを起動し、`SendMessage` が agentId
  指定で文脈を保ったまま再開（resume）する。
- Codex ほかのエージェント CLI: 起動＝委譲タスク/スレッドの開始。「resume」＝新規
  スレッドを立てず、同一スレッド・同一セッションへ再指示して文脈を引き継ぐこと。
- 検証コマンドは素の Git / シェルなので、どの環境でも使える。

## 手順

### 1. 委譲プロンプトの必須文言（予防・毎回）

サブエージェントへの委譲プロンプトには必ず入れる:

1. **「他エージェントへの再委譲禁止。あなた自身が Read/Edit/Write/Bash（またはこの
   環境の同等ツール）を実行すること」**
2. 排他的 checkout / worktree の絶対パス、成果物の絶対パス、受け入れ条件
   （何が存在すれば完了か）
3. 「完了報告には変更ファイル一覧を含めること」
4. 書式制約（UTF-8 BOMなし・追記のみ・上書き禁止など、壊されると困る条件）
5. **「checkout の所有権: 編集前に現在 branch と `git status --porcelain` を確認する。
   明示的に割り当てられていない既存 WIP、同じ checkout の別 writer、または
   所有権不明を検出した場合は、編集、commit、push、merge を行わず司令塔へ競合を
   報告する。続行前に排他的な checkout または隔離 worktree と task branch を
   割り当てること」**
6. **「完了検証baseline: 編集前に現在branch、`git rev-parse --verify HEAD`の完全OID、
   `git --no-optional-locks status --porcelain=v1 --untracked-files=all`の全出力を記録する。
   non-Git成果物と明示的に割り当て済みのdirty resume成果物では、実在、byte size、
   SHA-256も記録する。baseline取得にはread-only Git commandだけを使い、
   `git write-tree`などindex、working tree、object databaseを変更するcommandを使わない」**

これが防ぐ実測済みの失敗: 大きめのタスクを渡された background サブエージェントが、
自分で作業せずさらに子エージェントを起動し、「委譲したので完了を待ちます」とだけ
返して終了する。司令塔には成功に見える完了通知が届くが git 変更はゼロで、待機した
親と宙に浮いた子の分だけトークンを二重に消費する。

所有権の条項が防ぐ別の失敗: 2体の agent が同じ checkout を編集すると、互いの WIP を上書きしたり混入したりして、実測 diff と各完了報告が一致しなくなる。
委譲先へ明示的に割り当てられていない既存 WIP を stash、reset、削除、または委譲 task の commit へ含めてはならない。
同一 thread で resume した agent は、自身へ明示的に割り当て済みの WIP を継続できる。

### 2. 完了通知の検証（毎回・鵜呑み禁止）

- 編集開始前に§1の検証baselineを保持する。`HEAD`がまだ存在しないrepositoryは、OIDを
  捏造せずunbornと記録する。未割当WIPは開いたりhash化したりせず、所有権競合として
  委譲を停止する。
- 完了通知後、司令塔が最終branch、完全HEAD OID、`git diff --name-status
  <baseline>..<final> --`、現在の`git --no-optional-locks status --porcelain=v1
  --untracked-files=all`、受け入れ成果物の実在・内容・byte size・SHA-256を独立して
  再測定する。baseline HEADが存在する場合は`git merge-base --is-ancestor
  <baseline> <final>`のexit 0を必須とし、同じbranch名だけでhistory保持と判定しない。
- 証拠を合成する。HEAD、porcelain、assigned artifact stateがinitial→finalで不変なら、
  成果物が既に存在しても空振り。最終porcelainが空でも、HEADが変わり、
  baselineがfinal HEADのancestorで、baseline→final diffが割当済みpathだけを含み、
  成果物内容が受け入れ条件を満たせばcommit済みの成功とする。割当済みpathだけの
  diffでも、rewrittenまたはdivergent historyはscope違反とする。
  明示的に割り当て済みのdirty resumeは、porcelainに同じpathが出続け得るためartifact
  stateをinitial→finalで比較する。initial/final porcelainまたはcommit差分に未割当pathが
  あれば、成功ではなくscope違反とする。
- non-Gitのfile-changing taskは、編集前後の実在・byte size・SHA-256を比較してから
  内容を受け入れ条件と照合する。実在や更新時刻だけを完了証拠にしない。
- 通知文面だけで「完了」と報告しない。検証できない項目は「未検証」と明記する。

### 3. 空振りだったときのリカバリ

1. **同一エージェント**（同じ agentId / 同じスレッド）を resume し、「再委譲禁止。
   今すぐ自分で着手し、変更ファイル一覧を報告せよ」と再指示する（新規起動しない。
   文脈が残っている方が安くて速い）。
2. 2回目も空振りなら、そのタスクは司令塔が自分で実装する。

### 4. 実行環境差による無言失敗の切り分け

マルチエージェント連携では「送信成功＝到達・実行」ではない。実行側の環境を先に
確定する:

- `uname -a` / `command -v <tool>`（POSIX シェル）または `$PSVersionTable` /
  `Get-Command <tool>`（PowerShell）を**実行側の環境で**走らせ、シェル種別（WSL2 /
  Git Bash / PowerShell）と依存 CLI の有無を確認する。実測: 実行環境に依存 CLI
  （例: `sqlite3`）が無く、成功したフリの無言失敗になった例がある。
- Windows の Error 5 / EPERM は文面だけで原因を断定せず、失敗層（環境準備・
  プロセス起動・子プロセス runtime）をログで分けてから対処する。「フルアクセスを
  与える」を共通修復策にしない。

### 5. モデル・ルーティング（どこへ委譲するか）

委譲先は固定の役割分担ではなく、タスク特性で選ぶ:

- 並列調査・機械的一括作業: 安価または高速な汎用サブエージェント。
- 専門領域（例: フロントエンド実装）: 環境に専門エージェントがあればそれ。
- 司令塔の全文脈・判断・マージ権限が必要な作業: 委譲しない。

### 6. 台帳=委譲spec の並列委譲（大量修正へのスケール）

レビューで多数の指摘が出たら、台帳（ledger）に記録し、**台帳エントリをそのまま
自己完結した委譲 spec として渡す**。精密な台帳エントリは、それ自体が委譲 spec に
なっている。

台帳エントリの型（1指摘=1エントリ）:

```text
- [ ] <file>:<line> — <欠陥・症状を1行で>
      fix: <最小の修正案>
      confidence: <high|medium|low>
      verify: <通るべきテストまたはコマンド>
```

展開時のルール:

- **1リポジトリ=1エージェント**。並列エージェントにリポジトリを共有させない。
- 各エージェントは**隔離された git worktree とブランチ**で作業する。司令塔自身の
  checkout では作業させない。
- **マージは司令塔のみ**が行う。独立検証（テストの再実行または diff 精査）の後で。
- 委譲プロンプトには §1 の必須文言に加えて、次の4点を明記する:
  1. **mergeしない**（commit / branch / pull request の段階で止める）
  2. **worktree は残置**（後片付けしない。司令塔が検査できるように）
  3. **完了した台帳エントリを [x] 化する**（自分のリポジトリに属する台帳のみ）
  4. **実測のみ報告**（実際に走らせたテスト出力。推測は書かない）
- 台帳ファイルの書き手は常に1者に限定する: リポジトリごとに台帳を分ける（各
  エージェントは自分の台帳だけを [x] 化する）か、中央台帳は報告を受けた司令塔
  だけが [x] 化する。2体のエージェントに同じ台帳ファイルを書かせない。
- リモートの無いリポジトリでは「ブランチ残置 → 司令塔が fast-forward マージ」が
  安全で速い。

実測結果（1セッション）: 複数リポジトリの修正バックログに対し 14 体を並列展開し、
全員が空振りゼロ・全テスト緑で帰着 — 約40件の台帳エントリが 17 pull request +
ローカルマージ4件として一括で着地した。spec が精密だとエージェント側の良判断も
出やすい（例: 自分が追加するテストの文言が、自分が追加中のスキャナ規則に誤検出
されることを自己検出して修正した）。

## 安全条件

- 委譲対象タスクは (a) 対象リポジトリ内の編集に限定され、(b) secret / token /
  実データへのアクセスや外部送信を含まず、(c) 破壊的コマンド（一括削除・force push
  等）を含まないときだけ委譲する。満たさない場合は委譲せず司令塔が直接作業する。
- 委譲先 writer は排他的な checkout または隔離 worktree を所有する。別 writer、
  未割当の既存 WIP、所有権不明を検出した場合は、Git state と file を変更せず競合を
  報告する。
- リカバリの再指示は通常1回まで（§3。resume 後も空振りなら司令塔が引き取る）。
  同種失敗3回で停止して報告する上限（ハードストップ）を設ける。
- サブエージェントの報告にある「実行したという主張」は、検証済みと未検証を区別して
  扱う。

## 完了チェック

- 成果物が受け入れ条件どおり実在する(パス・内容・エンコーディング)。
- 編集前の branch/status と checkout の排他的所有を記録済みで、未割当の既存 WIP を
  変更も混入もしていない。
- 編集前baselineに完全HEAD OID、porcelain全出力、必要なartifact stateがあり、
  read-only commandだけで取得した。
- 最終HEAD/diff/current porcelainと成果物内容を司令塔が独立再測定し、assigned scopeの
  baseline HEADがfinal HEADのancestorであること、initial→final deltaが少なくとも1件
  あること、未割当pathを変更も混入もしていないことを確認した。
- 委譲先の報告と実測が一致している。不一致があれば原因を特定済み。
- 台帳モードでは、[x] 化されたエントリと「実際に検証してマージされた変更」が一致
  している。

## 報告

- 委譲先（モデル・ツール）と、その経路がタスク特性に合う理由。
- 検証方法と結果（porcelain 出力の要約・実在確認したパス）。
- 空振り・環境差トラブルが起きた場合はその症状・切り分け結果・リカバリ内容。
- 未検証の項目は「未検証」と明記する。
